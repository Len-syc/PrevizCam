# PrevizCam 镜头预检与防返工

这个 skill 只做一件事：在动第一个镜头之前，把“想拍的戏”变成“这个模型和这些占位人物真能拍的计划”。它不替代 `previzcam-previs-director` 的工具流程；先做完预检，再按导演 skill 创建草案、检查、取图并提交。

工具是 MCP 的 `list_workspaces`、`get_context`、`create_draft`、`update_draft`、`check_draft`、`render_frames`、`submit_draft`、`export_artifacts`、`get_job`。下文用简称指代它们。

## 先定交付契约

开工前用一句话说清楚，避免做完才解释：

- 这是**演示、覆盖测试，还是正式剪辑**？
- 白模/材质不完整是否可接受？还是要先修材质再拍？
- 时间轴顺序是什么？动作允许在多个镜头里重叠吗？
- 哪些镜头是“主镜”，哪些只是机位测试？
- 最终交付的是完整项目、单镜、还是覆盖样片？

把答案写进 `plan.name`、`plan.script.status`、`plan.script.coverageNote` 或镜头 `action`。覆盖测试不要包装成成片。

## 1. 先列约束表

从 `get_context` 的 `spatialContext`、剧本和素材里读，不要从文件名猜。至少列出：

| 约束 | 要确认什么 | 会卡住什么 |
|---|---|---|
| 人物朝向 | 每个 actor 的 `facing`；是否全局固定 | 转身、进门、面对面、反打 |
| 人物状态 | 同一角色的服装/伤/干湿能否用同一占位表示 | 跨场连续、红袍/病中状态 |
| 场景边界 | 门洞、门槛、台阶、地面尽头、背景是实景还是空场 | 低角度、远景、门外戏 |
| 遮挡物 | 门扇、柱子、屋檐、屋顶、树石 | 高角度、横移两端、前景构图 |
| 材质/光线 | GLB 是否有 baseColor；哪些物体有颜色/发光 | 白模下的可读性、暖色落点 |
| 道具 | 剧本要的物件是否真的存在 | 抱匾、书箱、茶盏、雨具 |
| 表演限制 | 占位人物无口型、无步态、无精细动作 | 点头、行揖、喂茶、倒地 |
| 可运动区域 | 走位和相机能走哪里；碰撞是近似的 | 跟拍、横移、穿过门洞 |

**最容易被忽略的是 `facing`。** 人物朝向是全局属性，`blocking` 只改位置，不改朝向。如果所有人物固定朝外，就不要写“他转身进门”“回头看一眼”的戏；要么换节拍，要么明确使用另一个状态占位，别假装能靠走位完成。

`spatialContext` 默认只给语义分组、包围盒、锚点、人物、镜头和网格统计。只有要按名称确认某道墙、某根柱、某扇门扇是否真的存在时才用 `get_context` 的 `spatial: {detail: "full", meshQuery, meshGroup, meshLimit, meshOffset}` 分页读取；不要为了“看全”把上千条网格拉回来。

## 2. 选节拍，不选“想要但做不到”的节拍

先问：这个模型的几何、朝向、材质和占位表演，支持哪一类戏？

- **固定朝外**：适合送行、背影、门外反向、空门、旁观者反应。具体 facing 值以场景数据为准（在这类山门项目中 0 常表示朝门外，但不要硬记）。
- **固定朝内**：适合归来、进门、面对门内的人。具体值同样以场景数据为准（常为 180）。
- **没有步态/脚部接触**：台阶只需少量关键点，不要逐级贴地。
- **没有表情/口型**：不要依赖近景表情；用背影、轮廓、视线、前后景和构图叙事。
- **门外没有完整山径/背景**：不要承诺“远去成点”“山道消失”；先说明只能拍到铺地边缘，或用门框/灯笼做收束。
- **白模**：不要靠材质区分门、墙、台阶；用灯笼、窗格、阴影、人物颜色和构图线。

如果节拍需要转身、倒地、抱匾、喂茶等占位做不到的动作，**先改节拍或加占位/道具**，不要先拍再补救。

## 3. 先写镜头清单，再编辑

每个镜头一行，写清楚：

`id｜叙事意图｜主体｜景别｜fov/焦段｜机位高度｜轴线/方向｜运动｜时长｜cast｜切点｜风险`

规则：

- 一批先做 **1 个主镜 + 2–4 个覆盖**（总共 3–5 镜），不要一次加十几个。
- 每个新机位只改变一个变量；不要同时换高度、焦段、轴线和运动。
- 运动镜头必须有叙事理由；默认固定机位。
- 覆盖测试要写清“主镜 + 哪些覆盖 + 是否重复动作”。
- 先定时间轴顺序：`plan.shots` 的数组顺序就是时间轴顺序，`update_draft` 整份替换 plan，所以重排、把主镜放前、把新镜头插到中间都只是调整数组顺序，没有追加式限制。

## 4. 每个新机位先 pilot 一帧

这是最省时间的一步。正式批量编辑前，先创建一份标明用途的 pilot 草案，只放一个临时 camera/shot（或只拍一帧）验证：

- 人物头顶、脚底、左右安全边；
- 人物在画面里的实际大小，不是纸面估算；
- 门洞/柱子/门扇/屋檐是否挡住主体；
- 高角度是否变成“平面图”；低角度是否只剩空背景；
- 横移两端是否被柱子或门扇遮挡；
- 门外是地面、天空，还是一片平背景；
- 屏幕方向、视线和轴线是否仍然成立。

`render_frames` 用 `view: "frames"` 配一个 `frames: [{shotId, progress}]` 就能只取这一帧，不必先把所有镜头都建好。

常见陷阱：

- **高角度**：机位太高会压成 floor plan；屋顶/门扇可能挡住演员。先试 3–3.5 米，再决定是否升高。
- **低角度**：门槛会挡住门外地面，低机位可能只看到空背景；先试门外低角度，或在院内留出门框/屋檐。
- **横移**：镜头在两端最容易撞柱/被门扇挡；先收窄范围，或把人物往中间挪。
- **广角主镜**：前景人物可能巨大且被裁切；先确认头顶和脚底。
- **反向**：机位要在轴线上或轴线附近；不要为了构图把人物左右关系剪反。

pilot 失败就改一个变量再试，不要直接批量加四镜。pilot 草案用完即弃，不要提交。

## 5. blocking 要省

- 只写**可见节拍**：起点、门槛/阶沿、铺地、终点。通常 4–6 个关键点足够。
- 静态人物一个 `t=0` 关键点即可。
- 不要为占位人物做脚部接触精度；没有步态，逐级贴地没有收益。
- 关键点越多，需要观察的截图越多，复核成本越高：每个关键点的 `t` 都是 `render_frames` 的必看时刻，`submit_draft` 会要求全部都看过。
- 不要在 `blocking` 里计划转身/回头；朝向是全局的。

## 6. 检查、截图、提交的纪律

1. 先 `check_draft`，修正 error；warning 要结合画面判断。
2. 截图先覆盖首、中、尾和相机/走位关键点。省略 `frames` 时 `render_frames` 会自动覆盖全部必看时刻并按整镜装批，首轮默认只回一张接触表；读返回的 `coverage`，确认每镜 `missingRequiredTimes` 为空。需要细节再用 `view: "frames"` 或具体 `frames` 补拍。
3. **逐张看**，不要用程序检查代替视觉判断。记录构图、景别、人物关系、视线、遮挡、背景。
4. 发现问题就先改 plan 再重新检查取图；修改会清空该版本的已看记录，需要重新覆盖必看时刻。
5. `submit_draft` 会拒绝还有必看时刻没渲染的版本，并逐个列出 `镜头 X 缺 t=…`；按它补拍后再提交，不要猜、也不要绕过。
6. 检查→截图→提交顺序执行；不要并行有状态的工具调用。
7. 连续三轮没有改善就保留当前成果并说明阻碍，不要虚报通过。未解决事项写进 `unresolved`。

## 7. 先做材质/背景审计

在构图前确认 GLB 主体材质是否有 `baseColor`。如果没有，工作台很可能呈白模：

- 先决定“白模预演可接受”，还是“先修材质/派生副本再拍”。
- 白模下用灯笼、窗格、深色木构、阴影、人物色块建立对比。
- 不要把“石阶/门框/山径”的可读性寄托在纹理上。
- 不要拍完十几帧才发现白模，再回头怀疑机位。

## 8. 剧本、时间轴、覆盖要保持一致

- 覆盖/测试镜头不一定在 `plan.script.shots` 里；如果不在，就在 `plan.name`、`script.status`、`coverageNote` 和镜头 `action` 里标明。
- 时间轴有 6 镜、剧本只有 1 个 material 时，不要把它说成“完整分镜”。
- 动作在多个覆盖镜头里重叠时，明确“这是覆盖测试，不是连续剪辑”。
- 角色状态（病中/康复/红袍）不能用同一个占位同时表示；需要时加状态占位，或在项目里明确“只做空间预演”。
- 如果最终需要故事顺序，创建草案时一次排好 `plan.shots`，不要等到交付前才发现顺序不对。

## 9. 什么时候该停下来问

遇到以下情况，先向用户确认，不要硬做：

- 节拍需要转身、倒地、精细手部/口型，而占位不支持；
- 需要门外山径、季节变化、雪/雨、道具，但模型没有；
- 同一角色跨场需要不同服装/状态，而项目只有一个占位；
- 白模/材质不可接受，需要先修资产；
- 用户说的“几个镜头”可能是正式分镜，也可能是覆盖测试，范围不清。

## 10. 预检输出模板

在第一次 `update_draft` 前，先写一个短块：

```text
交付：demo / 覆盖测试 / 正式段
约束：facing=…；场景边界=…；材质=…；道具=…；表演限制=…
选段：…（为什么这个节拍匹配约束）
镜头清单：
1. id｜意图｜主体｜景别｜fov｜高度｜轴线｜运动｜时长｜cast｜风险
2. …
pilot：先验哪一帧；如果失败改哪个变量
已知限制：…
```

这段文字能让用户在昂贵的编辑/截图循环前纠正方向。

## 11. 快速检查清单

- [ ] 交付契约写清楚了吗？
- [ ] 每个人物的 facing/state 都确认了吗？
- [ ] 选段是否依赖占位做不到的动作？
- [ ] 是否先做了每个新机位的 pilot 帧？
- [ ] 门扇/柱子/屋檐/门槛的遮挡是否验证？
- [ ] blocking 是否只保留可见节拍（4–6 个）？
- [ ] 截图是否覆盖首/中/尾和关键点，`coverage` 是否已无缺口？
- [ ] 修改后是否重新检查并重新覆盖必看时刻？
- [ ] 白模/材质/背景是否已说明？
- [ ] 覆盖镜头和剧本/时间轴是否一致？
- [ ] 交付时是否写清“这是预演/覆盖测试，不是人工验收”？

## 反例与正例

- **反例**：固定 `facing=0` 却设计“跨门报喜、转身对住持说话”，拍完才发现人物不能转身，整镜废弃。  
  **正例**：先确认朝向，改拍“送行/背影/门外反向”，或明确加一个朝内的状态占位。
- **反例**：主镜写 8 个 blocking 关键点，导致 8 个必看时刻、9 张截图；人物其实没有步态。  
  **正例**：4–5 个可见节拍关键点，台阶用插值，把时间留给构图。
- **反例**：在院内用低角度推空门，画面只剩蓝背景和白地。  
  **正例**：先 pilot，改到门外低角度缓升，让灯笼、门楣和空石阶进入画框。
- **反例**：横移从 -3m 到 +3m，两端被廊柱挡住主体，检查才发现。  
  **正例**：先试 ±2m，或把人物往中间挪，再决定运动范围。
- **反例**：拍完十几帧才发现 GLB 是白模，再猜是不是机位问题。  
  **正例**：构图前审计材质，先决定接受白模还是修材质。
- **反例**：为了省事先提交草案，被 `MISSING_FRAMES` 拒绝后反复重试同一版本。  
  **正例**：读错误里列的“缺 t=”，用 `render_frames` 精确补拍那几个时刻再提交。
